# TK-005 ESM Relative Import Extension Options (Discussion Draft)

- Status: active-discussion
- Date: 2026-03-19
- Scope: `packages/config` 与仓库级 ESM 导入规范
- Related Rule: `CS-005`

## 1. 背景

当前仓库采用 Node.js ESM 基线（`tsconfig: moduleResolution=NodeNext`），并在规范中要求相对导入必须显式带扩展名（例如 `./foo.js`）。

本讨论用于回答：

1. 保留扩展名的收益是什么？
2. 不保留会有什么问题？
3. 是否存在替代方案，以及各方案代价是什么？

## 2. 保留扩展名的主要好处

1. 运行时一致性更高
   - Node ESM 原生按“精确 specifier”解析；源码和运行时解析规则一致，减少“本地能跑、构建后报错”的偏差。
2. 降低工具链耦合
   - 不依赖 bundler/loader 的“自动补后缀”魔法，减少对单一工具行为的绑定。
3. 可预测性和可排障性更好
   - 导入路径即最终目标，错误更早暴露，定位路径问题更直接。
4. 更适合多包协作的长期维护
   - 在 monorepo 场景下，显式 specifier 可以避免隐式解析差异带来的跨包兼容问题。
5. 与当前仓库规则保持一致
   - 已有 `CS-005` 明确该约束；继续保留可避免规则与实现反复摇摆。

## 3. 不保留扩展名的主要问题

1. 原生 Node ESM 下容易直接报错
   - 若写 `./foo`，运行时可能出现 `ERR_MODULE_NOT_FOUND`（除非额外引入解析层）。
2. 增加环境分歧风险
   - IDE/测试/构建/运行时若采用不同解析器，容易出现“某环境可用、某环境失败”。
3. 隐式规则变多
   - 需要额外记住“谁在帮你补后缀”，团队认知成本上升。
4. 迁移成本后置
   - 早期偷省后缀，后续切换工具链或发布形态时常要集中补偿改造。

## 4. 可选替代方案

## 4.1 方案 A（当前方案）：继续保留显式扩展名

1. 做法
   - 相对导入统一使用 `./xxx.js`。
2. 优点
   - 规则清晰、运行时稳定、与 Node ESM 一致。
3. 缺点
   - 编写时视觉上稍“啰嗦”。
4. 适用
   - 原生 Node ESM 运行、长期治理优先的仓库。

## 4.2 方案 B：转为“无扩展名 + bundler 解析”

1. 做法
   - 源码写 `./xxx`，依赖 bundler（如 Vite/esbuild/tsup）在构建期解析。
2. 优点
   - 代码书写更接近部分前端生态习惯。
3. 缺点
   - 运行依赖 bundler 产物或额外运行时，工具链耦合提升。
   - 需要同步修改规范、脚本和 CI 基线，迁移面大。
4. 适用
   - 产物始终经过 bundler，且不依赖 Node 原生 ESM 直跑源码。

## 4.3 方案 C：保留无扩展名，但引入自定义 loader/运行时钩子

1. 做法
   - 通过 `--loader` 或等价机制在运行时补解析逻辑。
2. 优点
   - 代码可保持无扩展名。
3. 缺点
   - 部署与调试复杂度显著上升；可移植性变差。
4. 适用
   - 对运行时可控性要求高且能接受维护成本的团队。

## 4.4 方案 D：切回 CommonJS

1. 做法
   - 改为 CJS 生态（`require`）。
2. 优点
   - 相对导入扩展名约束变弱。
3. 缺点
   - 与当前 ESM 基线和长期架构方向冲突，迁移成本高。
4. 适用
   - 历史包袱严重且短期无法继续 ESM 的仓库。

## 5. 决策建议（讨论起点）

建议继续采用方案 A（保留显式扩展名），理由：

1. 与当前仓库 ESM 技术基线和 `CS-005` 一致。
2. 最小化短期迁移扰动，避免影响 TK-005~TK-011 的连续交付。
3. 在治理工具场景下，可预测性和跨环境一致性优先级高于语法简洁性。

## 6. 如果要改为“无扩展名”，最小迁移清单

1. 修改规范
   - 更新 `CS-005` 文本及相关治理说明。
2. 修改门禁脚本
   - 调整/替换 `check-esm-import-specifiers` 规则逻辑。
3. 修改编译与运行基线
   - 统一约束 `moduleResolution`、运行器、构建工具输出形态。
4. 修改现有代码
   - 批量迁移相对导入 specifier，并补回归测试。
5. 修改 CI 与文档
   - 保证本地与 CI 的解析行为一致，避免双标准。

## 7. 当前观察到的仓库状态（供讨论）

1. 规范中已声明 `CS-005`（强约束）。
2. `tsconfig` 为 `NodeNext` 基线。
3. `code_standards` 里的 `check-esm-import-specifiers` 已列入验证命令，但当前仓库 `scripts/governance/check-esm-import-specifiers.js` 尚未落盘，需要后续补齐或调整。
