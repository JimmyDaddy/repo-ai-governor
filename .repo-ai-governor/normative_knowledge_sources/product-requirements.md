## 1. 产品概述

Repo AI Governor 是一个可通过 npm 安装的 AI 开发治理工具，用于让接入该工具的代码库在使用各类 AI 编程助手、IDE、CLI Agent、自动化流程时，持续遵守统一的研发流程、代码规范、工程规范与团队协作要求。

工具既提供开箱即用的标准规范能力，也支持按项目特性插入自定义规范插槽，并支持在“辅助开发”和“全自动开发”两种模式下运行，适配主流模型、主流 IDE/工具以及多语言项目。

在产品定位上，Repo AI Governor 需要具备“流程化多 Agent 治理编排”能力：支持多 Agent 角色协同、可组合工作流编排（顺序/并行/循环）、策略驱动的人机闸口，以及可扩展的跨工具适配器。

## 1.1 治理对象与自举边界（v0.2 引入，v0.3 延续）

1. 主治理对象是“接入 Repo AI Governor 的任意代码仓库”。
2. 本仓库中的流程规则与门禁实现，应优先验证“工具如何规范目标仓库中的 AI 研发流程”。
3. 本仓库自身研发流程属于“自举验证场景”，用于回归工具能力，但不应替代产品目标本身。
4. 当“本仓库开发便利性”与“目标仓库治理正确性”冲突时，应优先保障后者。

## 2. 背景与问题

随着 AI vibecoding 普及，团队虽然获得了更高的编码速度，但也出现了以下问题：

1. AI 输出质量不稳定，代码风格、架构一致性和测试覆盖波动较大。
2. 同一个仓库在不同模型、不同 IDE、不同 Agent 工具下行为不一致。
3. AI 容易跳过关键流程，如技术方案、任务拆解、代码评审、自测、变更说明等。
4. 团队规范通常散落在 `README`、`CONTRIBUTING`、Wiki、口头约定中，AI 很难稳定遵守。
5. 不同项目对安全、发布、架构、领域知识的要求不同，缺少灵活的定制机制。
6. 想要进入自动化开发时，缺少明确的流程门禁、审计能力和回退机制。

## 3. 产品愿景

将“AI 开发规范”从文档约定升级为“可安装、可执行、可审计、可扩展”的治理系统，使多个 AI Agent 在任何协作入口中都像一支遵守团队流程的工程团队。

## 4. 产品目标

### 4.1 核心目标

1. 通过 npm 安装后，可快速在任意代码仓库启用治理能力。
2. 让 AI 在开发全流程中遵守预设规范，包括技术方案、任务拆解、编码、测试、代码评审、交付说明等。
3. 提供标准规范包，覆盖代码规范、工程规范、协作规范、交付规范。
4. 提供插槽机制，支持项目按语言、框架、团队流程、领域要求做自定义扩展。
5. 支持半自动与全自动两种开发模式。
6. 支持多模型、多 IDE、多 Agent 工具接入。
7. 支持多语言仓库与多自然语言使用场景。
8. 支持多 Agent 编排执行（Planner/Architect/Coder/Tester/Reviewer/Verifier 等）并具备明确角色边界。
9. 支持多工具 onboarding 与 role-agent projection，将 `connect / doctor / verify` 产物投影为可回放的 `AgentDescriptor` 供 CLI、report 与 diagnostics 共用。
10. 支持策略驱动的人机协同闸口，只在关键节点请求人工确认。

### 4.2 成功指标

1. 新仓库接入时间小于 15 分钟。
2. AI 生成代码的规范违规率明显下降。
3. AI 自动完成任务时的成功率、回滚率、人工介入率可被统计。
4. 团队可通过统一配置在多个仓库中复用规范。
5. 主流开发入口接入成本可控，新增适配器可插件化扩展。

## 5. 非目标

1. 不在第一阶段做成完整的云端 DevOps 平台。
2. 不替代现有 CI/CD、代码托管平台或静态检查器，而是编排并治理这些能力。
3. 不要求所有模型都具备完全一致的原生能力，允许通过适配层做能力降级。
4. MVP 阶段不承诺“完全离线且全能力自动开发”；离线能力优先覆盖本地治理检查与受限模式执行。

## 6. 目标用户

### 6.1 直接用户

1. 使用 AI 编程工具的个人开发者。
2. 希望统一 AI 开发流程的技术团队。
3. 需要让多个仓库共享研发规范的平台/基础设施团队。

### 6.2 间接用户

1. Tech Lead / 架构师：希望 AI 遵守架构约束和技术方案流程。
2. Reviewer / Maintainer：希望减少低质量 AI 代码进入主干。
3. 项目经理 / 交付负责人：希望 AI 任务执行可追踪、可审计、可回顾。

## 7. 典型使用场景

### 场景 1：新仓库接入

开发者执行 npm 安装和初始化命令，工具扫描项目语言、框架、目录结构与已有规范，生成基础治理配置与仓库专属 workspace，并把规范接入到 AI 使用入口中。默认使用工具托管 workspace，用户可切换为仓库内 `.repo-ai-governor`。

### 场景 2：AI 辅助开发

开发者在 IDE 中发起一个需求，工具要求 AI 先生成技术方案，再拆任务，再编码、自测、生成 CR 说明，最后才允许进入提交阶段。

### 场景 3：团队定制规范

团队在标准规范之外，新增“安全审查”“数据库迁移审批”“前端设计系统一致性”等插槽，让 AI 在特定项目中自动执行这些要求。

### 场景 4：AI 全自动执行

用户给出高层目标后，工具驱动 AI 自动完成方案、拆解、开发、测试、修复和任务记录回写；在关键门禁点根据策略自动继续或请求人工确认。

### 场景 5：跨工具一致治理

同一仓库在 Cursor、VS Code、Codex、Claude Code、Cline、Roo Code 等入口中，都能读取统一规范并表现出一致行为。

### 场景 6：评审复核升级闭环

AI 先完成方案与实现，再进入评审 Agent 与复核 Agent 的循环；若连续多轮复核仍不达标，自动升级到具备权限的人类 Reviewer 做最终裁决，并将结论回写到任务台账。

## 8. 核心能力需求

### 8.1 分发与安装

### 需求

1. 工具必须支持通过 npm 安装，至少支持：
   - 全局安装
   - 项目内 devDependency 安装
   - `npx` / `pnpm dlx` 直接执行
2. 提供初始化命令，为目标仓库生成基础配置、目录结构和默认规范文件。
3. 支持升级命令，便于同步新版本规范包与模板。

### 建议命令形态

- `repo-ai-governor init`
- `repo-ai-governor doctor`
- `repo-ai-governor check`
- `repo-ai-governor run`
- `repo-ai-governor review`
- `repo-ai-governor review-verify`
- `repo-ai-governor plan`
- `repo-ai-governor upgrade`

### 8.2 仓库治理激活

### 需求

1. 安装后，工具应能识别当前仓库是否已启用治理能力。
2. 初始化时自动生成治理配置，例如：
   - 全局产品配置
   - 仓库规范入口
   - 插槽定义
   - 自动化策略
   - 适配器配置
   - `AGENTS.md` 仓库级 AI 执行入口
3. 工具应支持检测现有规范文件并尽量复用，避免重复建设。
4. 提供“只读接入模式”，先做检查和提示，不强行改动项目。
5. workspace 持久化需支持双模式：
   - 默认 `tool_managed`：保存在工具为该仓库创建的独立 workspace 容器中的 `.repo-ai-governor/` 根目录，建议形态为 `~/.repo-ai-governor/workspaces/<repo_fingerprint>/.repo-ai-governor/`
   - 可选 `repo_local`：保存在目标仓库 `<repo>/.repo-ai-governor/`
6. 当用户未配置 workspace 模式时，必须默认使用 `tool_managed`。
7. 模式切换需支持迁移校验与回滚，避免状态丢失。

### 8.3 标准规范能力

### 需求

工具内置标准规范包，至少覆盖以下维度：

1. 代码规范
   - 命名、目录结构、注释策略、错误处理、日志策略、测试要求
2. 工程规范
   - 分支策略、提交规范、CI 检查、依赖管理、发布前检查
3. 研发流程规范
   - 需求理解、技术方案、任务拆解、实现、自测、代码评审、评审复核、任务记录回写
4. 质量规范
   - lint、类型检查、测试、覆盖率、性能、安全、回归检查
5. 协作规范
   - PR 描述、变更说明、风险提示、回滚方案、待确认问题

### 补充要求

1. 标准规范需支持版本化。
2. 规范内容既可供 AI 阅读，也可被工具执行。
3. 规范应区分“强约束”和“建议项”。
4. 每条规范应同时具备“人类可读视图”和“AI 可消费视图”，避免人机对规范理解不一致。
5. 仓库级 AI 规则入口应优先投影到 `AGENTS.md`，以适配主流 AI Agent 和 IDE。
6. `AGENTS.md` 应作为人类可读和 AI 可读的执行入口，而结构化配置仍是唯一事实源。
7. Standards Pack 需以同一份结构化规则资产统一生成“人类可读文档视图”“AI 可消费视图”和 `AGENTS.md` 投影视图。
8. Standards Pack 运行时至少应具备 `pack registry`、`rule renderer`、`agents projector` 三类职责边界；策略规则编译能力可作为独立模块扩展。
9. 官方规范包、团队共享规范包和仓库覆写规则必须具备可追溯的合并优先级与版本来源。

### 8.4 规范插槽机制

### 目标

让用户在标准规范之外，为项目增加定制能力，而无需修改核心框架。

### 需求

1. 支持定义插槽类型，例如：
   - 架构约束插槽
   - 安全合规插槽
   - 领域知识插槽
   - 测试策略插槽
   - 发布审批插槽
   - 文档产出插槽
2. 每个插槽至少支持以下能力：
   - 元信息定义
   - 触发条件
   - 适用范围
   - AI 提示词注入
   - 前置/后置检查
   - 是否阻断流程
3. 支持项目本地插槽、团队共享插槽、官方插槽。
4. 支持插槽优先级、依赖关系与冲突处理。
5. 支持插槽调试与测试，确保自定义规则可验证。
6. 插槽机制应采用“双轨制”：
   - 默认采用声明式配置，适合绝大多数规则场景
   - 高级场景允许脚本扩展，但需纳入权限和审计控制
7. 脚本扩展安全基线（必须满足）：
   - 权限白名单：仅可使用显式授权的 `filesystem/network/command/env` 能力
   - 资源配额：必须声明并执行 `max_execution_time_seconds`、CPU/内存/输出上限
   - 副作用声明：必须声明输入输出契约与 side effects 清单
   - 失败隔离：脚本异常不得污染主流程状态，必要时升级人工接管

### 8.5 流程编排引擎

### 目标

把 AI 开发过程从“自由对话”提升为“受控流程执行”，并具备流程化多 Agent 治理编排能力。

### 需求

1. 系统需支持标准阶段化流程：
   - 需求理解
   - 技术方案生成
   - 任务拆解
   - 实施开发
   - 自测与修复
   - Code Review
   - Review Verify
   - 任务记录回写
2. 系统需支持可声明的流程节点类型：
   - 顺序节点（Sequential）
   - 并行节点（Parallel）
   - 循环节点（Loop，必须声明 `maxCycles` 与 `maxWallTimeSeconds`）
   - 条件路由节点（Condition/Policy Route）
3. 每个阶段支持：
   - 输入定义
   - 输出要求
   - 通过条件
   - 失败重试策略
   - 人工确认点
4. 支持流程模板化，按仓库类型快速启用。
5. 支持跳步限制，避免 AI 直接越过方案或评审阶段。
6. 支持对子任务进行串行或并行编排。
7. 支持多 Agent 角色编排，每个角色至少声明：
   - 目标职责
   - 可调用工具集合
   - 可操作权限边界
   - 输出产物契约
8. 支持“确定性编排 + 智能执行”双层模型：
   - 编排层按预定义流程运行，保证可预测
   - 执行层允许具体 Agent 使用模型能力完成子任务
9. 编排运行时必须允许 `DSL/IR`、策略门禁、审计台账与底层执行后端解耦，避免 runtime backend 反向成为新的产品级事实源。
10. CLI 与未来桌面端应复用同一套本地 orchestration runtime/service；桌面 UI 只承担展示与人工决策交互，不直接拥有运行时主状态。
11. 任务拆解结果应支持按“当前执行项目 + 当前 sprint”生成目录化产物，至少包含：
   - 方案文档
   - 任务 checklist，采用单列表结构；每个任务条目至少包含任务编号、标题、负责人、优先级、截止日期、状态，并在条目下持续追加执行记录
   - CSV 任务记录，采用追加式执行台账；每条执行记录单独一行，至少包含 `execution_id`、`task_id`、`title`、`owner`、`priority`、`due_date`、`status`、`project`、`sprint`、`plan`、`result`、`verify`、`review_delta`、`recorded_at`
   - 单独 `review/` 目录中的 CR 文件，命名采用 `review_<slug>.md`
   - 复核结果直接追加到同一个 CR 文件中，并在状态流转时重命名为 `verified_review_<slug>.md`、`resolved_review_<slug>.md`
   - 若当前 worktree 的待收口 CR 明确仍归属于某个已 `completed` 的 stream，可在 `current-context.md` 中显式声明单值 `Worktree Review Target` 作为默认 CR 输出 override；当目标 `review/` 目录只剩 `resolved` 或无生命周期文件时，必须移除该 override

### 8.5.1 多 Agent 协议与运行时

### 需求

1. 提供统一 Agent 协议，屏蔽底层工具差异（Claude Code、GitHub Copilot、Codex 等）。
2. Agent 协议至少包含：
   - `agent_id`、`role`、`capabilities`
   - `allowed_tools`、`permission_level`
   - `input_schema`、`output_schema`
   - `error_contract`、`retry_policy`
   - `max_execution_time_seconds`、`token_budget`、`cost_budget`
3. 运行时应支持以下能力：
   - Agent 注册与发现
   - 会话级状态共享
   - 事件与产物追踪
   - 暂停/恢复与人工接管
4. 同一流程中允许混用不同 AI 工具实现不同角色 Agent，但必须服从统一流程和权限策略。

### 8.6 AI 全自动开发模式

### 目标

在受控前提下，让多 Agent 自动执行完整研发闭环，并在关键治理点强制人机协同。

### 需求

1. 支持自动模式与人工协作模式切换。
2. 自动模式下，工具可驱动 AI 完成：
   - 任务理解
   - 方案生成
   - 代码实现
   - 测试执行
   - 问题修复
   - 结果汇总
3. 提供分级授权机制，例如：
   - 只读
   - 可编辑代码
   - 可运行检查
   - 可提交变更
   - 可发起 PR
4. 提供门禁控制：
   - 关键变更需人工确认
   - 失败超过阈值自动停止
   - 高风险文件默认不自动修改
5. 支持策略化人工闸口（Human-in-the-Loop with Policy）：
   - 编码前必须完成方案评审通过
   - Review Verify 连续失败超过阈值后，自动升级人工评审
   - 涉及高权限变更时必须请求有权限 Reviewer 批准
   - 人工结论可回灌流程状态，决定“继续/重试/终止”
6. 对高风险变更的 HITL 触发必须先经过统一风险判定契约（Change Risk Evaluator），至少包括：
   - 输入事实：`changed_paths`、`file_categories`、`requested_permissions`、`command_class`、`lockfile_delta`、`migration_detected`、`ci_workflow_changed`、`release_script_changed`
   - 输出事实：`risk_level`、`risk_reasons`、`required_action`、`required_reviewer_roles`、`matched_policies`
   - 约束：适配器只负责采集事实，不得各自定义高风险判定语义
7. 提供审计记录：
   - AI 做了什么
   - 为什么这么做
   - 哪些规范被触发
   - 哪些检查通过/失败
8. 默认自动化权限边界应为：
   - 允许读取仓库、修改业务代码、测试代码和文档
   - 允许运行 lint、类型检查、测试、构建等本地质量命令
   - 允许在门禁通过的受控条件下自动提交、推送和发起 PR
   - 默认不允许自动修改密钥、基础设施配置和生产配置
   - 涉及依赖升级、数据库迁移、CI 配置、发布脚本、危险命令时必须人工确认

### 8.7 模型与工具适配

### 目标

让治理能力独立于具体模型和 IDE。

### 需求

1. 提供统一适配层，对接不同模型供应商和不同工具入口。
2. 第一阶段应优先覆盖主流入口：
   - IDE 类
   - CLI Agent 类
   - API 驱动类
3. 对不同模型能力差异做兼容处理，例如：
   - 上下文窗口大小
   - 工具调用能力
   - 结构化输出能力
   - 多轮规划能力
4. 对不同 IDE/工具提供统一规范注入方式，例如：
   - 系统提示模板
   - 仓库本地规则文件
   - 命令包装器
   - Hook/中间层
5. 提供适配器开发接口，支持社区扩展更多模型和工具。
6. 第一阶段建议优先支持以下入口：
   - Codex / Codex CLI
   - GitHub Copilot / GitHub Copilot CLI
   - Claude Code
7. 适配器需声明能力矩阵（是否支持工具调用、结构化输出、并行任务、流式输出等），供编排层做策略降级。
8. 当某工具不支持某类能力时，系统应自动降级或切换代理策略，而不是静默失败。
9. 支持网络受限模式（restricted network mode）：
   - 在无法访问外部模型服务时，仍可执行本地规则检查、流程编排与产物台账回写。
10. 支持本地模型适配路径（例如 Ollama 类本地推理入口）作为受限网络场景的可选执行面。

### 8.8 多语言支持

### 含义

这里的“多语言”包含两层：

1. 编程语言多语言：支持不同技术栈项目。
2. 自然语言多语言：支持中文、英文等不同语言的提示、规范、报告输出。

### 需求

1. 至少支持常见项目类型的治理模板，例如：
   - TypeScript/JavaScript
   - Python
   - Go
   - Java
   - Rust
2. 支持按语言/框架加载不同规范包与检查链路。
3. 输出文档支持多语言切换。
4. 插槽和模板支持国际化。
5. 规则内容应同时支持：
   - 面向 AI 的规范提示渲染
   - 面向人的规范文档渲染
6. 第一阶段建议至少支持中文和英文两套输出。

### 8.9 可观测性与报告

### 建议补充能力

1. 输出本次 AI 执行的流程报告。
2. 输出规范命中情况和违规情况。
3. 输出失败原因和修复建议。
4. 输出任务耗时、模型调用次数、人工介入点等指标。
5. 支持将结果写入本地文档、终端摘要或 CI 日志。
6. 支持将任务拆解结果写入项目/sprint 目录，并沉淀 checklist 与 CSV 台账。
7. 支持“依赖产物注册与追踪”：
   - 关键产物生成后自动登记（产物 ID、来源任务、版本、路径、状态）。
   - 产物与下游任务建立可检索依赖关系，并可输出依赖图。
8. CLI 输出需支持体验化渲染（进度、状态、风险提示）并可降级为纯文本，避免在非交互环境输出噪声控制字符。

### 8.9.1 CLI 输出体验基线

### 需求

1. 输出模式需至少支持：
   - `pretty`：面向交互式终端的人类可读美化输出（默认 TTY 场景）。
   - `plain`：纯文本输出（无颜色/无复杂控制符，适配日志采集）。
   - `json`：稳定 schema 的机器可读输出（适配 CI 与二次集成）。
2. CLI 需提供统一参数控制输出行为：`--output`、`--verbosity`、`--no-color`（或等价参数）。
3. `pretty` 模式至少应可展示：阶段进度、策略判定、人工介入点、结果摘要与错误修复提示。
4. 非交互场景（如 CI、重定向到文件）必须自动降级到 `plain`，除非显式指定 `json`。
5. 错误输出应包含结构化错误关键信息（如 `error_code`、`hint`、`next_action`），并保持人类可读描述。
6. 输出需与多语言能力对齐，支持按语言切换消息文本，不影响机器字段稳定性。

### 验收标准

1. 同一次执行在 `json` 模式下可产生稳定字段结构，便于 CI 解析。
2. `pretty` 模式在常见终端中具备可读性提升，且不影响命令退出码语义。
3. `plain` 模式不输出 ANSI 颜色控制符，日志平台可直接消费。

### 8.10 配置与版本治理

### 建议补充能力

1. 配置支持分层覆盖：
   - 官方默认配置
   - 团队配置
   - 仓库配置
   - 临时运行参数
2. 支持配置校验和迁移。
3. 支持规范包版本锁定与升级策略。
4. 支持回滚到旧版规则，降低升级风险。
5. 支持 workspace 模式与路径配置（`tool_managed/repo_local`）。

### 8.10.1 升级与迁移 UX 基线

1. Schema 迁移流程
   - `governor.yaml` 升级时，先执行 schema diff，再给出自动迁移建议与人工确认项。
2. 冲突处理流程
   - 当本地定制规则与新规范包冲突时，必须生成冲突清单（阻断项/可自动修复项/建议项）并提供可回放决策记录。
3. 回滚流程
   - 升级失败时支持一键回滚到升级前的配置快照与规范包版本。
4. 版本固定策略
   - 支持 pin 规范包主版本，按 minor/patch 自动跟随或手动升级。

### 8.10.2 依赖产物注册与消费机制

1. 依赖声明
   - 任务可声明 `depends_on_artifacts`，标识执行前必需产物集合。
2. 自动注册
   - 关键阶段产物生成后自动写入 Artifact Registry，并记录 `producer_task` 与 `artifact_version`。
3. 执行前解析
   - 任务启动前自动解析依赖产物，注入执行上下文。
4. 缺失处理
   - 依赖产物缺失、版本不兼容或状态非 active 时，按策略触发 `block` 或 `HITL`。
5. 审计要求
   - 产物注册、依赖解析、缺失处置必须写入审计事件并可回放。
6. 生命周期退出机制
   - `artifact_status` 至少支持 `active/frozen/deprecated/archived/retired`，并具备可执行状态迁移规则。
   - 主注册表仅保留可消费或短期过渡产物（`active/frozen/deprecated`），历史产物迁移到归档注册表。
   - 依赖解析命中 `deprecated/archived/retired` 时，默认不自动注入上下文，按策略触发 `warn/block/HITL`。
7. 单一事实源约束
   - canonical registry 固定为 machine-readable main/archive registry，可由 sqlite 等等价 durable backend 承担，不得并行维护第二份手工 registry 台账作为事实源。
   - human-readable artifact view 仅允许由 canonical registry 动态渲染或查询生成，不得承担独立状态维护职责。

### 8.10.3 三层文档同步机制（需求 -> 方案 -> 架构）

1. 同步范围
   - `.repo-ai-governor/normative_knowledge_sources/product-requirements.md`
   - `.repo-ai-governor/normative_knowledge_sources/repo-ai-governor-overall-technical-solution.md`
   - `.repo-ai-governor/normative_knowledge_sources/repo-ai-governor-architecture-and-repo-layering.md`
2. 同步规则
   - 三层文档任一层发生需求语义变更时，必须在同一变更集中同步其余两层。
   - `.repo-ai-governor/normative_knowledge_sources/product-requirements.md` 变更时，必须同步 `.repo-ai-governor/normative_knowledge_sources/product-requirements-brief.md`。
   - 方案层允许拆分为“总技术方案北极星索引 + `technical-solution-module-registry` + module overview/contract 文档”，但 `north_star_change / layer_boundary_change` 仍必须升级到 triad 同步。
   - module contract 变更需具备 impact classification 结果，至少同步 producer module overview，并显式给出 direct consumer / triad 的推荐或强制同步面。
3. 工具内置机制
   - 提供可执行门禁检查（三层文档一致性检查 + brief 同步检查）。
   - 支持机器可读输出（CI 阻断）与人类可读输出（本地定位）。
4. 失败策略
   - 默认策略为 `block`：检测到部分同步或元数据不一致时阻断交付。
   - 支持后续扩展 warning 模式用于迁移窗口。
5. 审计要求
   - 同步检查结果需进入执行审计，便于回放和追踪。

## 9. 用户故事

1. 作为个人开发者，我希望通过一条命令初始化工具，这样我能快速让仓库进入可治理状态。
2. 作为团队负责人，我希望 AI 先出技术方案再写代码，这样团队可以在实现前控制方向。
3. 作为 Reviewer，我希望 AI 自动跑完规范检查并生成变更摘要，这样我能把精力集中在关键问题上。
4. 作为平台工程师，我希望通过插槽机制给不同项目注入差异化规则，这样无需维护多套工具。
5. 作为自动化使用者，我希望 AI 在符合门禁时自动推进，在高风险操作前暂停确认，这样效率和安全可以兼顾。
6. 作为国际化团队成员，我希望输出内容可按语言切换，这样不同地区成员都能顺畅协作。
7. 作为技术负责人，我希望能定义“多轮复核失败后必须人工介入”的策略，这样可以确保质量底线。
8. 作为治理管理员，我希望不同 Agent 可由不同工具实现但服从统一流程，这样可以避免工具锁定并持续演进。
9. 作为一线开发者，我希望 CLI 输出更清晰易读并支持可切换模式，这样我可以更快定位问题并在 CI 中稳定消费结果。
10. 作为治理负责人，我希望需求/方案/架构文档同步由工具自动校验，这样可以避免需求漂移与实现偏航。

## 11. 建议的信息架构

可按以下模块拆分产品架构：

1. CLI 核心层
   - 安装、初始化、检查、执行、升级、输出模式编排
2. Governance Engine

   - 插槽注册、解析、注入、冲突处理
5. Adapter Layer
   - 模型适配器、IDE 适配器、Agent 适配器
6. Automation Controller
   - 自动模式、权限控制、审计日志
7. Reporting Layer
   - 报告、指标、执行摘要、CLI 展示输出、CI 输出
8. Shared Layer

## 12. 建议的配置模型

建议支持如下配置对象：

1. `product config`
   - 产品级开关、默认行为、版本信息
2. `repo config`
   - 当前仓库流程、语言、规则启用情况
3. `standards config`
   - `pack_sources`
   - `merge_precedence`
   - `render_targets`（`human/ai/agents`）
   - `projection_targets`（如 `AGENTS.md`）
4. `slot config`
   - 插槽定义、优先级、触发条件
5. `role registry config`
   - `roles`
   - `versioning_policy`
   - `alias_resolution`
   - `deprecation_policy`
   - `migration_policy`
6. `adapter config`
   - 对接模型、工具、IDE 的参数
7. `automation config`
   - 自动执行策略、权限级别、门禁规则
8. `i18n config`
   - 默认语言、术语映射、输出语言
   - `runtime_engine`（默认 `i18next`）
9. `workspace config`
   - `mode`（`tool_managed`/`repo_local`）
   - `tool_managed_root`（工作区容器根，governor 根目录位于 `<tool_managed_root>/<repo_fingerprint>/.repo-ai-governor`）
   - `repo_local_root`（默认 `<repo>/.repo-ai-governor`）
   - `migration_policy`（copy/verify/switch/rollback）
10. `artifact dependency config`
   - `registry_enabled`
   - `auto_register_patterns`
   - `dependency_resolution_policy`（block/escalate/warn）
   - `artifact_version_policy`（strict/compatible/latest）

## 13. 非功能需求

1. 可扩展性
   - 新增语言、模型、IDE、插槽时不应改动核心架构
2. 稳定性
   - 配置错误、模型失败、检查失败时应可恢复并给出明确反馈
3. 安全性
   - 敏感路径、危险命令、高风险操作必须可控
4. 可审计性
   - AI 的关键行为需要留痕
5. 可移植性
   - 支持不同操作系统和常见 Node.js 运行环境
6. 性能
   - 初始化、检查、执行反馈应在可接受时延内
7. 易用性
   - 新手可以快速上手，专家可以深度定制

### 13.1 数据隐私与审计日志保留策略

1. 默认保留周期
   - 审计日志默认保留 `90` 天（可配置）。
2. 脱敏要求
   - 日志中的敏感信息（如 token、密钥、个人识别信息）必须在写入前脱敏。
3. 删除与导出
   - 支持按 `execution_id/project/sprint/date range` 执行审计记录导出与删除。
4. 合规扩展
   - 企业场景可按地区法规（如 GDPR 等）覆盖保留周期与删除策略。

## 14. 风险与挑战

1. 不同模型的能力差异较大，可能导致执行一致性不足。
2. 不同 IDE/Agent 工具的开放能力不同，适配成本可能高。
3. 如果规范过重，可能影响用户的使用意愿。
4. 自动化能力越强，对权限治理、回退机制和审计要求越高。
5. 多语言、多框架、多团队规范叠加后，配置复杂度容易失控。

## 15. 建议的 MVP 方案

建议第一阶段聚焦“本地 CLI + 仓库治理 + 多 Agent 流程编排 + 插槽 v1”，控制范围如下：

1. 提供 npm 包和 CLI。
2. 支持初始化仓库治理配置。
3. 提供标准研发流程模板（含顺序、并行、循环）。
4. 提供标准规范包。
5. 支持基础插槽注入。
6. 支持 Codex / GitHub Copilot / Claude Code 首批接入。
7. 支持关键人工闸口：方案评审、复核升级、有权限 CR。
8. 支持基础 CI 集成。
9. 支持本地执行报告输出。

这样可以先验证两个关键问题：

1. 多 Agent 编排是否能显著提升复杂任务稳定性和可维护性。
2. 人工闸口策略是否能在效率与风险之间取得平衡。
3. 插槽机制是否足够灵活，能覆盖不同项目的差异化需求。

## 16. 后续里程碑建议

### 里程碑 1：可安装可初始化

目标：完成 npm 包、CLI 骨架、初始化能力、基础配置模型。

### 里程碑 2：流程治理跑通

目标：跑通方案生成、任务拆解、开发、自测、评审复核和任务记录回写的最小闭环。

### 里程碑 3：插槽机制上线

目标：支持项目自定义规则插槽，并可参与流程门禁。

### 里程碑 4：主流工具适配

目标：接入多个主流 AI 开发入口，统一规范注入体验。

### 里程碑 5：自动模式上线

目标：支持有门禁的自动执行模式，并补齐审计与回退。

## 17. 关键决策

### 17.1 产品定位：先做本地工具，再向团队平台演进

两者区别如下：

1. 本地工具
   - 以 npm 包和仓库本地配置为核心
   - 直接服务开发者的 IDE、CLI 和本地工作流
   - 上手快、部署轻、适合先验证产品价值
2. 团队平台
   - 以组织级规范分发、统一审计、可视化管理为核心
   - 需要中心化配置、权限体系、指标看板
   - 价值更大，但复杂度和建设成本更高

当前决策：

1. 第一阶段明确定位为“仓库内可安装的本地治理工具”。
2. 架构上预留“团队平台”扩展能力，例如共享规范包、远程策略源、集中审计接口。
3. 不在 MVP 阶段引入重型云端依赖，避免拖慢落地速度。

### 17.2 第一批必须支持的入口

第一阶段明确支持以下开发入口：

1. Codex / Codex CLI
2. GitHub Copilot / GitHub Copilot CLI
3. Claude Code

支持策略如下：

1. 优先支持“规范注入”和“流程约束”能力。
2. 通过适配器对不同工具做差异化兼容，不要求底层实现完全一致。
3. 在执行计划中单列“后续适配路线图”，提前规划更多 IDE、CLI Agent 和 API 驱动入口。
4. 后续扩展应优先复用统一适配器接口，避免为单个工具做一次性实现。

### 17.3 规范插槽：默认声明式，补充脚本扩展

两者区别如下：

1. 声明式配置
   - 更容易理解、审查、版本管理和跨仓库复用
   - 更适合做规则组合、优先级和冲突治理
   - 安全性和可预测性更高
2. 脚本扩展
   - 更灵活，适合复杂判断、外部系统联动、动态逻辑
   - 成本更高，也更容易引入不透明行为和安全风险

当前决策：

1. 默认以声明式配置作为主路径。
2. 为高级用户保留脚本扩展能力。
3. 脚本扩展必须具备权限控制、执行审计和失败隔离机制。
4. 脚本扩展必须采用权限白名单机制，未授权能力默认拒绝。
5. 脚本扩展必须声明资源预算（执行时长、CPU、内存、输出大小）并由运行时强制执行。
6. 脚本扩展必须声明副作用清单，执行结果写入审计日志并支持回放追踪。

### 17.4 自动模式默认权限边界

当前决策把默认权限边界放在“可编辑代码 + 可运行本地检查 + 可自动交付低风险变更”。

默认允许：

1. 读取仓库内容。
2. 修改业务代码、测试代码、文档和部分本地配置。
3. 执行 lint、类型检查、测试、构建等质量命令。
4. 在门禁通过后自动提交 commit。
5. 在门禁通过后自动 push。
6. 在门禁通过后自动发起 PR。

默认不允许：

1. 自动修改 secrets、生产配置、基础设施配置。
2. 自动执行危险命令或不可逆操作。

必须人工确认的高风险场景：

1. 依赖升级和锁文件大变更。
2. 数据库迁移。
3. CI 工作流修改。
4. 发布脚本和部署配置修改。
5. 跨目录大规模重构。

### 17.5 CI 集成：第一天就支持

当前决策为“需要”，并纳入 MVP。

最小 CI 集成能力应包括：

1. 提供适合 CI 调用的检查命令。
2. 返回稳定的退出码，便于阻断流水线。
3. 输出机器可读和人类可读两类结果。
4. 支持在 CI 中生成执行摘要和违规报告。
5. 支持在本地终端启用 `pretty` 模式美化输出，并在 CI 默认回退到 `plain/json`。

CI 平台覆盖策略：

1. MVP（P0）：提供 GitHub Actions 一等模板与示例。
2. P1：补齐 GitLab CI 与 Jenkins 官方模板。
3. P2：补齐 Azure Pipelines 与 CircleCI 参考模板。
4. 其他 CI 平台通过通用 CLI 调用协议接入（不阻断主流程能力）。

### 17.6 多语言输出：规则既给 AI 读，也给人读

规则提示不应只服务 AI，也不应只服务人，而应来自同一份规范资产的双视图渲染：

1. 面向 AI 的视图
   - 用于系统提示、上下文注入、流程约束和执行策略
2. 面向人的视图
   - 用于文档阅读、审查确认、团队协作和培训沉淀

当前决策：

1. 第一阶段同时支持中文和英文。
2. 规则底层应尽量结构化存储，再分别渲染为 AI 提示和人类文档。
3. 避免维护两套语义不一致的规则文本。

### 17.7 多 Agent 策略：编排层统一，执行层开放

当前决策：

1. 编排层保持统一协议和流程控制，确保治理一致性。
2. 执行层允许接入任意 AI 工具实现不同角色 Agent，避免厂商锁定。
3. 人工闸口由策略引擎统一管理，而不是散落在各工具脚本中。
4. 当工具能力不足时，优先降级执行策略，再考虑阻断流程并提示人工接管。

### 17.8 三层文档同步：约束前置，防止实现漂移

当前决策：

1. 需求、方案、架构三层文档是同一事实链路，禁止单点更新。
2. 工具需内置可执行检查，避免仅靠人工约定。
3. PRD 变更必须同步简版 PRD，确保 AI 执行入口不失真。
4. 默认使用阻断策略，确保“文档事实源”先于实现推进。
5. 模块方案拆分不能引入第二套事实源；模块依赖关系必须由结构化 registry 统一管理。

## 18. 一句话总结

Repo AI Governor 的本质不是另一个 AI 编程工具，而是一层“流程化多 Agent 开发治理基础设施”：让任意工具实现的多个 Agent 在进入仓库后，都按团队定义的流程、权限和人工闸口协同工作。
