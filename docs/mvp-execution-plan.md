# AI 开发治理工具 MVP 执行计划

- 文档版本：v0.1
- 状态：草案
- 日期：2026-03-12
- 关联文档：[product-requirements.md](./product-requirements.md)

## 1. 目标

本执行计划用于把 PRD 中已经确认的 P0/MVP 范围拆解为可执行的研发工作流、阶段里程碑和 backlog，目标是在不引入重型云端平台的前提下，交付一个“仓库内可安装的本地治理工具”最小可用版本。

MVP 的核心目标如下：

1. 以 npm 包形式发布，并提供可用的 CLI。
2. 支持仓库初始化、配置加载、环境自检和治理检查。
3. 跑通“方案生成 -> 任务拆解 -> 开发约束 -> 自测 -> 评审 -> 评审复核 -> 任务记录回写”的最小治理闭环。
4. 提供标准规范包、双语渲染和声明式插槽机制。
5. 首批支持 Codex / GitHub Copilot / Claude Code 三类入口。
6. 支持基础 CI 集成、报告输出和后续扩展接口。
7. 支持按“项目 + sprint”生成任务产物目录，包含 checklist、CSV 台账和单独的 `code-review/` 目录，以及状态化 CR 文件命名。

## 2. 范围边界

### 2.1 MVP 纳入范围

1. 本地 CLI 工具与 npm 包发布能力。
2. 仓库级配置和初始化能力。
3. 标准流程模板与治理执行引擎最小版本。
4. 标准规范包 v1。
5. 声明式插槽机制 v1。
6. 报告输出与基础 CI 集成。
7. Codex / GitHub Copilot / Claude Code 首批适配。
8. 中文、英文双语输出。

### 2.2 MVP 暂不纳入范围

1. 组织级云端管理平台。
2. 可视化后台、指标看板和规范市场。
3. 完整无人值守的自动开发闭环。
4. 团队共享规范的远程同步服务。
5. 脚本型插槽的正式发布版。

### 2.3 MVP 的自动化边界

MVP 阶段只需要把自动化能力需要的权限模型、门禁模型和审计模型设计清楚，并在接口层预留扩展点；完整的自动模式 `v1` 放在 MVP 之后推进。

## 3. MVP 完成定义

只有同时满足以下条件，才视为 MVP 可交付：

1. 用户可以通过 `npm install`、`npx` 或 `pnpm dlx` 使用工具。
2. 工具可以在一个空仓库或已有仓库中执行初始化并生成基础治理配置。
3. 工具可以执行环境检查和治理检查，并返回稳定退出码。
4. 工具可以根据治理流程模板生成计划、检查执行结果，并同步回写 checklist / CSV 与输出报告。
5. 标准规范包和插槽机制可以在至少一个示例仓库中跑通。
6. Codex / GitHub Copilot / Claude Code 三类入口都有明确的接入方式和验收样例。
7. 工具可以在 CI 中运行，并产出机器可读和人类可读结果。
8. 核心文档、默认模板和输出报告支持中文和英文。
9. `plan` 命令可以按当前项目和 sprint 输出任务目录，至少包含方案文件、任务 checklist、任务 CSV、单任务文件和 `code-review/` 目录。

## 4. 交付原则

1. 本地优先：先把仓库内体验做扎实，再考虑平台化能力。
2. 声明式优先：规则、配置和插槽优先结构化表达，减少隐式逻辑。
3. 单一事实来源：同一份规范资产同时渲染给 AI 和人阅读。
4. 低耦合扩展：模型适配器、语言模板、插槽机制都必须可插拔。
5. 风险可控：高风险行为默认不自动执行，所有关键行为应可审计。
6. 先跑通再做深：优先完成最小闭环，再扩展更多语言、工具和自动化场景。

## 5. 研发主线

建议按 7 条主线并行推进：

### 5.1 CLI 与发布主线

目标：交付可安装、可执行、可升级的 Node.js CLI。

MVP 输出：

1. npm 包基础结构。
2. CLI 入口和命令分发。
3. 版本信息、帮助命令、错误码规范。
4. 初始化、检查、计划、评审、升级等基础命令框架。

### 5.2 仓库治理主线

目标：让任意仓库可以被识别、初始化和加载治理配置。

MVP 输出：

1. 仓库配置文件格式。
2. 初始化脚手架。
3. 配置加载、校验、迁移和覆盖策略。
4. 只读检查模式。
5. `AGENTS.md` 生成或更新机制。

### 5.3 流程与规范主线

目标：把研发流程从松散提示提升为可执行治理链路。

MVP 输出：

1. 流程模板 v1。
2. 标准规范包 v1。
3. 计划生成、评审检查、评审复核、任务记录回写与报告输出的最小闭环。
4. 中英文双视图渲染能力。

### 5.4 插槽主线

目标：支持项目在不改核心框架的前提下做定制化治理。

MVP 输出：

1. 声明式插槽模型。
2. 插槽加载与优先级处理。
3. 官方示例插槽。
4. 插槽调试和校验基础能力。

### 5.5 适配器主线

目标：让首批工具能统一读取治理规则。

MVP 输出：

1. 统一适配器接口。
2. Codex / GitHub Copilot / Claude Code 三类接入样例。
3. 规范注入策略。
4. 后续适配路线图。

### 5.6 报告与 CI 主线

目标：让工具既能本地运行，也能在 CI 中稳定执行。

MVP 输出：

1. 终端摘要输出。
2. 机器可读报告文件。
3. CI 可调用命令。
4. 示例 CI 配置模板。

### 5.7 任务产物组织主线

目标：让任务拆解结果以稳定目录结构沉淀，便于按项目和 sprint 管理。

MVP 输出：

1. 项目/sprint 目录生成规则。
2. `plan.md`、`tasks/checklist.md`、`tasks/tasks.csv` 等标准文件。
3. `tasks/` 子目录中的单任务文档。
4. `code-review/` 子目录中的状态化 CR 文件，例如 `review_tk-001-initialize-sprint-templates.md`。
5. 可由 CLI 和 CI 复用的稳定路径约定。

建议默认结构：

```text
docs/
  mvp/
    sprint-001/
      index.md
      plan.md
      tasks/
        checklist.md
        tasks.csv
        TK-001.md
      code-review/
        review_tk-001-initialize-sprint-templates.md
```

任务记录约定：

1. `tasks/checklist.md` 使用单列表，不按状态分组。
2. 每个任务条目至少包含任务编号、标题、负责人、优先级、截止日期、状态。
3. 每次执行、复核、修复都以 `执行记录` 追加在同一任务条目下。
4. `tasks/tasks.csv` 采用追加式执行台账，每条执行记录一行。
5. CSV 字段至少包含 `execution_id`、`task_id`、`title`、`owner`、`priority`、`due_date`、`status`、`project`、`sprint`、`plan`、`result`、`verify`、`review_delta`、`recorded_at`。

CR 文件状态流转约定：

1. 初始生成：`review_<slug>.md`
2. 复核完成：`verified_review_<slug>.md`
3. 问题处理完成：`resolved_review_<slug>.md`
4. `<slug>` 应包含任务编号或变更主题，避免同一 sprint 下文件冲突
5. 复核内容直接追加在同一个 CR 文件中，不再生成单独的 `review-verify.md`

## 6. 里程碑计划

以下节奏按 1 到 2 名核心工程师、8 周左右周期估算；如果资源更充足，可以把阶段并行压缩。

### 里程碑 M1：项目骨架与 CLI 基础

目标：先把工具作为一个可运行的 npm CLI 建起来。

范围：

1. 创建包结构、构建脚本、发布基础配置。
2. 建立 CLI 命令路由。
3. 统一日志、退出码、错误处理。
4. 输出最小 README 和使用说明。

退出标准：

1. 可本地执行 CLI。
2. 可打包并模拟 npm 分发。
3. 命令帮助信息完整。

### 里程碑 M2：仓库激活与配置模型

目标：让仓库可以被初始化并加载治理配置。

范围：

1. 设计配置 schema。
2. 实现 `init`、`doctor`。
3. 支持只读扫描模式。
4. 支持配置校验和默认值填充。

退出标准：

1. 示例仓库可以成功初始化。
2. 配置错误时有明确报错。
3. 可以识别是否已启用治理。

### 里程碑 M3：流程模板与标准规范包

目标：跑通最小治理闭环。

范围：

1. 实现流程模板结构。
2. 实现标准规范包 v1。
3. 提供 `plan`、`review`、`review-verify`、`check` 基础能力。
4. 实现中英文规范和报告渲染。
5. 实现按项目/sprint 输出任务目录。

退出标准：

1. 用户可对一个任务生成技术方案和任务拆解。
2. 用户可执行治理检查并获得结果。
3. 规范可同时面向 AI 和人渲染。
4. 任务拆解结果可以自动写入项目/sprint 目录。

### 里程碑 M4：插槽机制与报告输出

目标：让项目可以在标准规范之外增加差异化规则。

范围：

1. 实现声明式插槽格式。
2. 实现插槽注入和优先级规则。
3. 输出终端摘要和 JSON/Markdown 报告。
4. 补齐示例插槽和验收样例。

退出标准：

1. 至少 2 个示例插槽可在流程中被触发。
2. 插槽冲突有明确处理策略。
3. 检查结果可写入报告文件。

### 里程碑 M5：首批适配器与 CI 集成

目标：完成 MVP 的外部接入能力。

范围：

1. 定义统一适配器接口。
2. 提供 Codex / GitHub Copilot / Claude Code 接入样例。
3. 提供 CI 命令和示例工作流。
4. 完成首个 npm 发布候选版本。

退出标准：

1. 三类入口都有可运行样例或接入模板。
2. CI 中可稳定调用检查命令并阻断失败。
3. MVP 具备对外试用条件。

## 7. 模块拆解

### 7.1 CLI Core

建议首批命令：

1. `repo-ai-governor init`
2. `repo-ai-governor doctor`
3. `repo-ai-governor check`
4. `repo-ai-governor plan`
5. `repo-ai-governor review`
6. `repo-ai-governor review-verify`
7. `repo-ai-governor report`
8. `repo-ai-governor upgrade`

MVP 要求：

1. 命令输出风格统一。
2. 支持非交互式模式，便于 CI 调用。
3. 错误码可预测。
4. 能生成或更新仓库根目录 `AGENTS.md`。

### 7.2 配置系统

建议支持以下配置文件：

1. 产品级默认配置。
2. 仓库级治理配置。
3. 插槽配置。
4. 适配器配置。
5. 执行上下文配置。
6. 国际化配置。

MVP 要求：

1. 支持 schema 校验。
2. 支持默认值合并。
3. 支持版本字段和迁移入口。

### 7.3 Governance Engine

MVP 支持的阶段：

1. 需求理解。
2. 技术方案。
3. 任务拆解。
4. 实施开发。
5. 自测。
6. Code Review。
7. Review Verify。

MVP 要求：

1. 每个阶段有输入、输出和通过条件。
2. 至少支持串行执行。
3. 失败时返回明确阶段状态。

### 7.4 Standards Pack

MVP 范围：

1. 代码规范。
2. 工程规范。
3. 流程规范。
4. 质量规范。
5. 协作规范。

MVP 要求：

1. 规范底层结构化。
2. 同时支持 AI 视图和人类视图。
3. 支持中文、英文渲染。

### 7.5 Slot Engine

MVP 范围：

1. 声明式插槽定义。
2. 触发条件。
3. 适用范围。
4. 阻断策略。
5. 优先级。

MVP 要求：

1. 明确官方插槽和项目插槽的覆盖关系。
2. 插槽冲突时返回可读解释。
3. 预留脚本扩展接口，但不作为 MVP 承诺功能。

### 7.6 Adapter Layer

MVP 范围：

1. 统一适配器接口。
2. 规则注入模板。
3. 工具差异化兼容层。

MVP 要求：

1. 三类首批入口至少完成规则注入和基础流程约束。
2. 适配器层不依赖特定模型供应商实现。
3. 新适配器接入不需要改核心治理逻辑。

### 7.7 Reporting Layer

MVP 范围：

1. 终端摘要。
2. Markdown 报告。
3. JSON 报告。
4. 任务 checklist。
5. CSV 任务台账。
6. `code-review/` 目录中的状态化 CR 文档。

MVP 要求：

1. 报告至少包含执行阶段、命中规范、失败原因、下一步建议。
2. CI 可直接消费 JSON 结果。
3. 任务拆解相关产物可按项目/sprint 稳定落盘。

## 8. MVP Backlog

以下 backlog 建议直接作为首批 issue/任务池。

### EPIC A：CLI 与工程底座

#### A1. 初始化 npm 包和 CLI 入口

- 优先级：P0
- 目标：创建可发布的 Node.js CLI 工程骨架。
- 验收：
  1. 可执行 `repo-ai-governor --help`。
  2. 具备版本输出和基础命令注册。
  3. 可生成本地构建产物。

#### A2. 建立统一日志、错误码和命令执行框架

- 优先级：P0
- 目标：为本地和 CI 运行提供一致行为。
- 验收：
  1. 正常、警告、错误输出可区分。
  2. 退出码语义稳定。
  3. 非交互模式可运行。

#### A3. 建立 npm 发布与版本管理流程

- 优先级：P0
- 目标：让工具具备可发布基础能力。
- 验收：
  1. 支持打包和本地安装验证。
  2. 发布前检查可执行。
  3. 版本号和升级说明机制明确。

### EPIC B：仓库激活与配置系统

#### B1. 设计治理配置 schema

- 优先级：P0
- 目标：定义仓库配置、插槽配置、适配器配置的核心结构。
- 验收：
  1. schema 可校验。
  2. 包含版本字段。
  3. 支持默认值。

#### B2. 实现 `init` 命令和仓库脚手架

- 优先级：P0
- 目标：一条命令生成治理基础文件。
- 验收：
  1. 新仓库可生成默认配置。
  2. 已有仓库不会被危险覆盖。
  3. 支持只读预览模式。

#### B3. 实现 `doctor` 命令

- 优先级：P0
- 目标：检查当前仓库是否满足运行条件。
- 验收：
  1. 能检查 Node.js、配置文件、关键目录。
  2. 输出问题列表和修复建议。

### EPIC C：流程编排与标准规范

#### C1. 定义流程模板 DSL 或配置模型

- 优先级：P0
- 目标：用结构化方式描述治理流程。
- 验收：
  1. 可定义阶段、输入、输出、门禁。
  2. 支持最小串行执行。

#### C2. 实现标准规范包 v1

- 优先级：P0
- 目标：覆盖代码、工程、流程、质量、协作规范。
- 验收：
  1. 规范结构化存储。
  2. 可区分强约束和建议项。
  3. 支持双语。

#### C3. 实现 `plan` 命令

- 优先级：P0
- 目标：生成技术方案和任务拆解输出。
- 验收：
  1. 输出包含目标、方案、风险、任务列表。
  2. 按项目/sprint 生成目录化产物。
  3. 输出格式可被报告层消费。

#### C4. 实现 `check`、`review` 和 `review-verify` 命令

- 优先级：P0
- 目标：执行治理检查、评审检查和评审复核。
- 验收：
  1. 可对当前仓库输出检查结果。
  2. 失败项可定位到规则或阶段。
  3. 支持评审复核结果追加回同一 CR 文件并更新状态命名。

### EPIC D：插槽机制

#### D1. 实现声明式插槽模型

- 优先级：P0
- 目标：支持项目级扩展规则。
- 验收：
  1. 插槽支持元信息、触发条件、适用范围、阻断标记。
  2. 插槽配置可单独校验。

#### D2. 实现插槽加载与优先级处理

- 优先级：P0
- 目标：让官方插槽和项目插槽可以组合运行。
- 验收：
  1. 冲突时有稳定优先级规则。
  2. 输出冲突解释。

#### D3. 提供示例插槽

- 优先级：P0
- 目标：验证插槽机制不是纸面能力。
- 验收：
  1. 至少提供安全审查和文档产出两个示例插槽。
  2. 能在示例流程中被触发。

### EPIC E：适配器与注入机制

#### E1. 设计统一适配器接口

- 优先级：P0
- 目标：定义各类工具的接入边界。
- 验收：
  1. 输入输出模型清晰。
  2. 可独立新增适配器。

#### E2. 完成 Codex / Codex CLI 接入样例

- 优先级：P0
- 目标：完成首个主流入口接入。
- 验收：
  1. 支持规则注入。
  2. 支持流程模板接入说明。

#### E3. 完成 GitHub Copilot / GitHub Copilot CLI 接入样例

- 优先级：P0
- 目标：覆盖第二类主流入口。
- 验收：
  1. 有明确接入模板或规则文件方案。
  2. 有验收示例。

#### E4. 完成 Claude Code 接入样例

- 优先级：P0
- 目标：覆盖第三类主流入口。
- 验收：
  1. 有明确接入模板或规则文件方案。
  2. 有验收示例。

### EPIC F：报告与 CI

#### F1. 实现统一报告模型

- 优先级：P0
- 目标：统一本地与 CI 输出结果。
- 验收：
  1. 支持终端摘要、Markdown、JSON 三种输出。
  2. 包含阶段状态、命中规范、失败原因、建议动作。

#### F2. 提供 CI 调用命令

- 优先级：P0

## 9. 推荐实施顺序

为了尽快跑通最小闭环，建议按以下顺序开工：

1. A1 -> A2 -> B1 -> B2
2. C1 -> C2 -> C3
3. C4 -> F1 -> F2
4. D1 -> D2 -> D3
5. E1 -> E2 -> E3 -> E4
6. A3 -> F3

这样安排的原因是：

1. 先建工程底座和配置系统，避免后面返工。
2. 先跑通流程和规范，再接入工具适配器。
3. 报告和 CI 尽早纳入，方便持续验证。

## 10. MVP 验收用例

建议至少准备以下验收场景：

1. 新建一个 TypeScript 示例仓库，执行初始化并生成治理配置。
2. 在示例仓库中运行 `doctor`，确认环境与配置检查可用。
3. 对一个示例需求执行 `plan`，生成技术方案和任务拆解。
4. 对一个示例需求执行 `plan`，并在 `docs/mvp/sprint-001/` 生成目录化任务产物。
5. 对示例仓库执行 `check` / `review` / `review-verify`，生成终端摘要和 JSON 报告。
6. 启用示例插槽，验证插槽命中和冲突处理。
7. 在 CI 中运行治理检查，验证退出码和报告文件。
8. 在 Codex / GitHub Copilot / Claude Code 三类入口中完成一次规范注入验收。

## 11. 主要风险与应对

### 风险 1：不同工具的接入方式差异大

应对：

1. 先定义统一适配器接口。
2. 首批只承诺“规则注入 + 流程约束”能力。
3. 对工具差异做降级兼容。

### 风险 2：规则系统过重，影响用户采用

应对：

1. 默认提供轻量模板。
2. 强约束和建议项分离。
3. 支持只读检查模式。

### 风险 3：插槽机制过早复杂化

应对：

1. MVP 仅支持声明式插槽。
2. 脚本扩展只保留接口，不做正式承诺。
3. 用官方示例插槽验证通用性。

### 风险 4：CI 与本地行为不一致

应对：

1. 本地和 CI 共享同一命令入口。
2. 报告模型统一。
3. 在示例仓库里同时跑本地和 CI 验收。
